# Delivery ledger and durable handoff

Use this reference before implementation dispatch and after each integration result. Root owns the ledger and accepted demand; planning, implementation, Quality, and Delivery owners produce the changes and verification evidence. Follow explicit user limits on publication or merge.

## Establish readable inputs

Verify the actual target repository/base and its exact revision. Start the planning/integration workspace clean. If work already exists in a dirty checkout, preserve that checkout and its diff before continuing in an isolated workspace; do not reset or clean it as a setup step.

When push and remote publication are authorized, establish one remote specification/integration branch and its draft PR before dispatch. Have the planning owners commit and push the accepted scheme, necessary specification and Agent Notes, and applicable frozen UI draft reference plus experience route. A linked ticket supplies requirements, but each writer's accepted input must be readable at the recorded planning revision; conversational history alone is insufficient.

Confirm the remote branch exists at the recorded SHA, the planning checkout is clean, the draft PR targets the verified base, and every implementation input is accessible before assigning a ready writer. When push or remote publication is outside scope, use an equivalent frozen local integration revision and accepted local ledger; do not publish merely to satisfy the remote procedure.

## Maintain one ledger

Keep one concise ledger in the delivery PR or linked issue, or the accepted local record when publication is outside scope. Each required delivery unit records accepted scope, owner session, branch/worktree, exact input and result revisions, evidence, current state, blocker, and next discriminating check. Preserve accepted criteria unless the user changes scope. Evidence records include the behavior, environment, and mode actually observed; a later head does not relabel them.

Group related tickets under one module owner. A ready frontier includes only units whose blockers are already integrated into the recorded planning/integration revision. Hand off the exact revision, accepted ticket criteria, relevant source pointers, retained scratch references, read/write scope, and completion evidence. Verify a writer's reported pushed head before treating its work as remotely delivered.

The ledger records replacement reasons and marks the prior owner replaced or complete before another writer takes that mutable scope. Writers may use bounded read-only investigators; proposed splits into additional write owners return to Root for a separate ledger row and isolated workspace.

## Integrate and supervise

Delivery alone integrates completed owner commits into the demand branch. Before an integration batch, verify the live base and incorporate required base movement centrally through the accepted merge strategy. Send the resulting exact integration revision to affected in-flight owners; sibling owners do not each choose a different base. After integration, recompute the ready frontier, refresh affected checks and reviews, and dispatch newly unblocked work.

Root keeps active owners supervised through bounded waits and completion/attention events until results have been observed and incorporated. A child needing human action reports its ticket/ledger row, the concrete action, and the evidence; Root surfaces that request rather than leaving the user to inspect another session. Waiting for required user input may pause dependent work; an unobserved background worker is not a completed handoff.

Complete an integration unit only when its exact result is on the demand branch or it has a concrete recorded blocker. Before final readiness, the PR or accepted local ledger identifies the specification and completed delivery units, all required results and evidence are accounted for, and no selected worker remains unobserved. A published delivery PR carries the applicable closing references; a local record does not close remote tickets. Final acceptance, review, retrospective, merge verification, and cleanup remain governed by ODD.
